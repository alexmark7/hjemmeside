About the project.

Binderly is a SEP1 student software engineering project about keeping track of the cards you own — a local Java desktop app built by a small team, for collectors.

This page is the public work log: the problem, the decisions, the technical boundaries, and what is still open.

01 · The collector problem

It started with a binder that stopped making sense.

Binderly came out of a broad SEP1 brief: work as a small team, gather requirements, design an application, build it, and test it. Choosing the problem was up to us, so we picked one we could describe from the inside.

Collections do not get out of hand all at once. A binder fills, a shoebox appears, then a second box of doubles. Variants and conditions multiply the record-keeping: the same card can sit in a collection three times and still be three different things.

Somewhere in the middle of that, the questions get small and constant:

  • Is this a card I already own, or a variant I do not have?
  • How many copies are actually in the binder?
  • Which copy is in the best condition?
  • Which numbers am I still missing from this set?
  • Where did that card go?

Binderly's answer is a digital binder that mirrors the physical one. Every entry names the card, its variant, its condition, and how many copies you own, and every entry can be found by name or card number.

The SEP1 process, in four passes.

Requirements → Architecture & UI → Implementation → Verification. Each pass produced something the next one could check, and findings sent the team back a step.

  1. Requirements

    Collector interviews, scope, priorities, and the feature-status list that keeps “planned” separate from “in the app”.

  2. Architecture & UI

    A catalogue-versus-collection data model, screen flows, and the visual language used by the app and this website.

  3. Implementation

    The Java application, local storage, and this static project site — kept small enough for one team to finish and explain.

  4. Verification

    Feature checks against the brief, an accessibility pass, defect notes, and the guides that document the intended workflow.

The four stages ran as short loops. A test failure could send the team back to requirements; a new requirement could change the interface.

02 · Product philosophy

Collecting is the point, not the price tag.

Binderly is a tool for organising a collection you already enjoy. It is deliberately not a tool for turning that collection into an investment.

Think about the table after a swap with a friend: a small stack of new cards, two of them doubles, one a variant you already own in worse condition. The job is to get them into the binder accurately — not to work out what they might be worth.

Built for In scope

One accurate record of the cards you own.

  • Knowing exactly which cards you own, and how many copies of each.
  • Keeping variants and conditions apart, so a holo copy is never confused with the standard print.
  • Finding a specific card in seconds instead of flipping through binders.
  • Seeing which cards are still missing from a set you are collecting.

Deliberately left out Out of scope

A marketplace, a price guide, a social network.

  • No marketplace: no listings, offers, trades, or sales.
  • No price tracking, valuations, or investment charts.
  • No social feed, follower counts, or sharing prompts.
  • No accounts, no sign-in, and no cloud sync.

03 · Technical architecture

A Java desktop application, kept deliberately small.

The application is a program on your computer, not a website you sign into. That keeps the project small: one person, one local collection, and no server in the middle.

Confirmed 5 statements

What we can state today.

Platform
A Java desktop application.
Where it runs
Locally, on the computer where the application runs.
Storage
Collection data is saved locally on that computer.
Users
Single-user: one person and one local collection, with no shared accounts.
Backend
None. No server, no online account, and no sign-in.

These points come from the project brief and define the boundary the team is building inside.

The project is split into four areas of responsibility, from planning and requirements through to testing and documentation.

Team member one

Project lead · requirements

Owns the plan and the requirements: keeps the scope realistic, records the team's decisions, and checks that each feature traces back to something a collector would actually use.

  • Scope
  • Decisions
  • Traceability

Team member two

Java application developer

  • Catalogue
  • Collection records
  • Local saving

Team member three

UI & front-end developer

06 · Specification roadmap

Specified now, planned later.

This table separates what is in the app from what is still planned. It is a specification roadmap, not a release promise.

Feature status for Binderly v0.1.0. “In the app” means the feature is described in the project plan and targeted at the first release; “Planned” means it is not part of the current build. On a narrow screen, scroll the table sideways to read the status column.
Feature What it covers Status
In the app 8 core features
Collection records Every copy you own, with variant, condition, and quantity kept as one entry per combination. In the app
Card catalogue The list of cards that can be added to the collection, described by expansion, number, type, and stage. In the app
Card details A detail view for a card, bringing its catalogue information and your own copies together. In the app
Editing entries Changing the quantity or condition of an entry, and removing one after a confirmation step. In the app
Search Finding an entry by full or partial card name, or by card number. In the app
Sorting Reordering the current view by name, expansion, number, HP, condition, or quantity. In the app
Filtering Narrowing the collection by expansion, type, stage, condition, or variant. In the app
Local saving Writing collection changes to storage on your own device, so they are there in the next session. In the app
Planned 6 candidate features
Import & export Backing the collection up to a file and restoring it later. An import is intended to replace the current collection only after a clear confirmation. Planned
Local card images Attaching your own photo of the physical card to an entry, stored on your device. Planned
Manual card entry Adding a card the catalogue does not list, without waiting for the catalogue to be updated. Planned
Collection statistics Counts and charts about the collection, such as totals per expansion or per card type. Planned
Catalogue updates Importing a newer catalogue file when new sets are added. Planned
Merging entries Combining two entries for the same card, variant, and condition into one. Planned

The second group is planned only. Those features are planned but are not part of the application today, and they are not promised for the first release.
